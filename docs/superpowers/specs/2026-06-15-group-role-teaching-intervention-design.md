# 小组协作角色教学干预设计

日期：2026-06-15

## 背景

当前 CoThink 已经支持学生小组讨论、AI 1v1 对话、教师端对话记录、CSV 导出和基础学习分析。新需求希望借助 AI 或平台机制区分小组协作中的对话者角色，并为后续研究编码提供基础。

本阶段先服务教学干预，而不是直接建设研究编码系统。原因是：如果小组本身没有有效协作，后续编码只能记录“协作不足”，难以反向改善课堂活动。第一版应先让学生在小组中明确自己该承担的协作功能。

## 目标

让每个小组成员获得一个清晰的本轮协作角色，并在讨论过程中得到对应行动提示。系统默认自动分配角色，教师可以手动调整，学生可以对分配提出异议但不能自行改角色。

成功标准：

- 学生进入小组后能看到自己的协作角色、角色说明和行动提示。
- 同一小组内角色尽量均衡，避免所有成员承担同类角色。
- 教师能在小组管理中查看并修改成员角色。
- 学生能提交角色异议，教师能查看并处理。
- 第一版不引入语音识别、实时说话人分离或完整研究编码工作台。

## 第一版角色集合

第一版使用五个协作学习角色：

| 角色 | 学生任务 | 行动提示方向 |
|---|---|---|
| 推进者 | 推动小组进入下一步 | 询问是否可以确定方案、进入下一阶段或分配下一步 |
| 提问者 | 发现不清楚的地方 | 提出让讨论更深入的问题 |
| 解释者 | 把观点讲清楚 | 补充原因、例子、证据或操作步骤 |
| 质疑者 | 找漏洞和反例 | 检查观点是否证据不足、条件不完整或存在反例 |
| 总结者 | 阶段性归纳共识 | 总结当前共识、分歧和下一步 |

暂不加入“资料员”。当前资料、任务和小组讨论尚未强绑定，资料员容易成为空角色。等课程资料引用和任务证据链更稳定后再加入。

## 用户流程

### 学生侧

1. 学生创建或加入小组。
2. 如果该成员没有协作角色，系统自动分配一个角色。
3. 学生端小组讨论页显示“我的本轮角色”。
4. 聊天输入区域附近显示该角色的简短行动提示。
5. 学生可以点击“提出异议”，选择原因并可填写补充说明。
6. 异议提交后，学生看到待教师处理状态。

学生不能直接修改自己的角色。这样可以避免学生集中选择压力较低的角色，保留教师对课堂分工的最终判断。

### 教师侧

1. 教师在小组管理中查看每个小组的成员角色。
2. 教师可以手动修改某个成员的角色。
3. 教师可以查看学生提交的角色异议。
4. 教师处理异议时可以保留原角色、改为指定角色，或触发该小组重新均衡分配。
5. 处理结果对学生端可见。

## 自动分配规则

第一版使用“随机 + 小组内均衡”的规则：

1. 读取同一小组内已有成员角色。
2. 优先从当前小组内使用次数最少的角色中随机选择。
3. 当成员数大于角色数时允许角色重复，但尽量让各角色数量接近。
4. 教师手动设置的角色不被自动覆盖，除非教师主动触发重新分配。
5. 学生退出或转组时，保留历史异议记录，但新小组角色按新小组重新分配。

该规则足够透明，也便于教师理解和修正。

## 数据设计

复用现有 `groups`、`group_members` 和 `users` 关系，第一版只给小组成员增加当前协作角色字段，并新增异议记录。

建议字段：

- `group_members.collaboration_role`：当前协作角色，允许为空以兼容旧数据。
- `group_members.role_assigned_by`：`system` 或 `teacher`。
- `group_members.role_assigned_at`：最近一次分配时间。

建议新增表：`group_role_objections`

- `id`
- `group_id`
- `user_id`
- `current_role`
- `reason`
- `note`
- `status`：`pending`、`resolved`、`rejected`
- `resolution_note`
- `created_at`
- `resolved_at`
- `resolved_by`

## 接口设计

学生接口：

- `GET /groups/{group_id}/role`：获取当前学生在该组的角色、说明、行动提示和异议状态。
- `POST /groups/{group_id}/role-objections`：提交角色异议。

教师接口：

- `GET /teacher/groups`：在现有小组成员返回中增加协作角色和异议摘要。
- `PATCH /teacher/groups/{group_id}/members/{user_id}/collaboration-role`：教师修改成员协作角色。
- `GET /teacher/group-role-objections`：查看角色异议列表。
- `POST /teacher/group-role-objections/{id}/resolve`：处理异议。
- `POST /teacher/groups/{group_id}/collaboration-roles/rebalance`：教师触发该组重新均衡分配。

## 前端设计

学生端小组讨论页：

- 在小组讨论标题或输入区上方显示当前角色。
- 展示一句角色说明和一句行动提示。
- 提供“提出异议”入口。
- 异议提交后显示“待教师处理”状态。

教师端小组管理：

- 在成员列表中增加“协作角色”列。
- 角色显示为可编辑选择框。
- 显示该成员是否有待处理异议。
- 提供处理异议入口。

不在第一版新增独立研究编码页。对话记录页后续可以基于角色数据增加筛选和导出字段。

## 后续迭代

第二阶段可以统计角色行为是否发生：

- 总结者是否发出阶段总结。
- 质疑者是否提出质疑或反例。
- 提问者是否提出问题。
- 推进者是否推动阶段转换。
- 解释者是否补充理由或证据。

第三阶段再建设对话编码：

- AI 初步标注发言行为。
- 教师或研究人员修正编码。
- 导出带角色、行为标签、时间和小组信息的 CSV。

语音实时记录、说话人分离和线下课堂转写作为更后期能力，不进入第一版。

## 验证计划

后端验证：

- 新成员加入小组时能自动获得角色。
- 小组内角色分配保持均衡。
- 教师修改角色后不会被系统自动覆盖。
- 学生提交异议后教师能处理。

前端验证：

- 学生端能看到角色和提示。
- 学生端能提交异议并看到状态变化。
- 教师端能查看、修改角色并处理异议。

教学验证：

- 课堂试用中观察学生是否更清楚自己该做什么。
- 比较角色上线前后小组发言均衡度和总结、质疑、提问等行为出现情况。
- 收集教师对角色是否可控、学生对角色是否理解的反馈。
